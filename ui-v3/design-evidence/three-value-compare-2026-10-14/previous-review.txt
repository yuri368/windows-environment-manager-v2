1. 阻断问题：删除最后一个元素后，变量仍然存在
需要修复

位置：demo-plan.js 的 build()，约第 134–140 行。
demo-plan.js

复现代码可直接在当前演示页的开发者控制台运行：

JavaScript
const target = { scope: 'User', name: 'TEST' };
const snapshot = {
  exists: true,
  raw: 'A',
  type: 'REG_SZ',
  revision: 1
};

const baseline = DemoPlan.captureBaseline({
  target, mode: '-append',
  snapshot, selectedRaw: 'A'
});

const plan = DemoPlan.build({
  target, mode: '-append',
  snapshot, selectedRaw: '',
  baseline
});

console.log(plan.operations, plan.after);

按当前源码，结果为：

REMOVE A

after.exists === true

after.raw === ''

但根据此前约定的“撤销最后一个非空元素后删除变量键”规则，在没有需要保留的空元素时，预期应是：

after.exists === false

after.raw === null

这不是标签问题，而是冻结计划的最终状态错误。执行后，历史可能显示空字符串，而非变量不存在。

最小修复： 明确最终元素列表为空与保留原始空元素的区别，统一 build() 和显式元素编辑器的删除边界，并补回归测试。不要把所有空字符串一律解释成删除，因为用户明确创建空变量也是合法操作。

2. 同目标批量仍存在一个特殊类型冲突漏洞

位置：demo-plan.js 的 buildBatch()，约第 165–180 行。
demo-plan.js

当前冲突检测检查了 replace 与 append 混用，以及多个 replace 目标值不同的情况，但没有拒绝同一目标同时出现 special=true 和 special=false。

可复现输入：

JavaScript
const plan = DemoPlan.buildBatch({
  target: { scope: 'User', name: 'Path' },
  snapshot: {
    exists: true,
    raw: 'OLD',
    type: 'REG_EXPAND_SZ',
    revision: 0
  },
  requests: [
    { id: 'a', mode: 'replace', whole: false, selectedRaw: 'NEW' },
    { id: 'b', mode: 'replace', whole: true, selectedRaw: 'NEW' }
  ]
});

console.log(plan.valid, plan.kind, plan.issues);

当前实现会接受该组合，因为两个请求都是 replace，目标字符串也一致。

但此前已有规则是：同一个 Windows 变量不能同时被普通变量与 Special 变量管理。

最小修复： 在同目标批量计划中增加 Special 一致性校验，发现混用直接禁止确认。无需重构配置模块。
