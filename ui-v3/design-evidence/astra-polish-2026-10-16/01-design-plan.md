# Astra 第 1 轮：预览决策层与工作台改进方案

日期：2026-10-16。审阅基线：56dbf603。仅分析，本轮不改产品代码。

已审阅根规范、ui-v3/AGENTS.md、架构优先级、V3.1/V3.2/V3.3、无缝刷新、状态跟进与展示移动契约；结合 temp.html、demo-plan.js、shell-ui.css、surface-ui.css、ui-polish.css 及既有工作台/600px预览截图。旧截图仅用于设计参照，不作为最新源码验收证明。

## 判断与设计方向

目前的元素铭牌、三值对照、原文展开、键盘元素导航已有完整视觉语言。继续增加阴影、渐变或动效的收益很小。真正缺口是：用户必须阅读多组长 Path 才能判断“本次会改变什么、哪些意图尚未完成、现在该做什么”。

本轮统一以“执行前审阅单”为设计方向：顶部用一条紧凑状态带给结论，中部保留高密度逐目标证据，底部将确认动作与实际完成范围绑定。沿用绿色系统，不重做导航、侧栏、编辑器或业务模型。

## 1. P0：预览顶部的决策摘要与目标索引

代码入口：temp.html 的 renderPreview、previewRowMarkup、showPreview；样式集中追加到 surface-ui.css，避免修改多套基础 token。

预览标题下增加独立的紧凑审阅区，直接回答：本次有多少目标会变化、多少不变、多少存在待处理事项。统计单位明确为“目标”，不要把请求、元素和目标混成一个总数。可另显示真实 operations 的“追加 N / 删除 N / 整值替换 N”，整值替换不能算作逐元素替换。

状态优先级：

1. 非法 plan 或 append 排序限制：`本次暂不能应用`，列出具体阻塞目标。
2. reviewedVersion != version：`预览已更新，请重新核对`，保留原有独立 review → confirm 两步。
3. 有 duplicate/shared/continuity：`可应用安全变更 · 部分删除将保留`；若所有 operations 均为空，则写`当前值不会改变 · 删除意图仍待处理`。
4. 有 operations：`已准备好 N 个目标的变更`。
5. 无 operations 无 issue：`当前值无需改变`，仍允许现有“确认选择”语义，不擅自禁止保存成功来源/偏好。

目标索引：同一行或下一行放 `用户 · Path`、`系统 · Path` 等短按钮，带“变化 / 保留待处理 / 不变 / 阻塞”的文字和小图形，点击只滚动并聚焦对应目标标题。使用 targetKey 作为稳定 DOM 关联，不以临时排列索引作为唯一身份。不对 rows 排序，不过滤 frozen rows，不改变确认范围。超过 5 个目标时允许换行或用原生折叠“全部 N 个目标”，不新增横向滚动条。

目标卡标题由当前的“全部应用名 / 方案名 · 变量”改成：变量名为主、作用域铭牌紧随；应用/方案成员放独立次行。这样批量共享 Path 在600px不再产生又长又难扫的标题。

验收：批量目标数与冻结 rows 一致；User/System同名不合并；无变化与被保护未删除不会显示为已完成删除；索引跳转不写入、不关闭、不改变版本；冻结 before/after/operations 与旧行为逐项一致。

## 2. P0：让“删除保留”说明可理解、可定位、可返回处理

目前 planSummary 将三类情况统称“仍有 N 项删除保留，需在元素编辑器中确认”，不足以解释风险，且不能把打开编辑器暗示为一次万能确认。

在有 issues 的预览目标卡中，比较值上方增加一块低饱和琥珀说明。工作台同样复用这个只读说明生成器。每行展示准确的 issue.value（code、可断行）、原因、当前处理结果；actualIndexes 若显示必须加1且只称“当前位置”，不能宣称是持久身份。

| reason | 主文案 | 下一步说明 |
| --- | --- | --- |
| duplicate | 存在重复，未自动删除 | 相同内容对应多个位置；当前副本均保留。如需删除，请在元素编辑器核对具体行。 |
| shared | 其他选定方案仍使用，已保留 | 本次删除未执行。请先核对其他方案的选定值；不得根据 issue 推测应用所有权。 |
| continuity | 无法确认仍是原元素，已保留 | 当前值已发生变化，原删除依据不再可靠；同文本重新出现也不恢复自动删除资格。 |
| stale / conflict | 当前上下文不兼容 / 批量目标冲突 | 列出涉及目标与已知模式/成员，返回工作台检查；不产生虚构 after。 |

共享问题目前不携带具体保护者身份，不要为了说明擅自用近似字符串推断保护者。对于很多 issue，前2项可直接显示，其余放原生 details，并让摘要明确剩余条数。

预览提供 `返回工作台检查`，只关闭预览、定位对应应用/方案/变量、展开对照并将焦点落到变量输入或对照标题；不得自动改变 source、mode、selectedRaw、勾选范围或直接应用。批量目标可定位首个有关成员；文案不承诺已解决整个批量问题。append 工作台可用现有“编辑元素”，replace 必须继续隐藏/禁止该入口。

确认按钮旁给一行范围说明：`仅应用本页列出的实际变更；上述删除继续保留`。含部分保留且有实际操作时，按钮可用 `模拟应用安全变更`；不要用“全部完成”。弹窗取消和返回检查保留编辑意图。保留现有部分完成历史、原基线与输入。

验收：分别构造三类 issue；after 必须保留相应元素；导航前后输入、baseline、removalState一致；检查 replace 不能通过新入口绕过编辑限制；点击返回不创建历史；部分应用后 issue 仍显示、无错误成功状态。

## 3. P1：工作台加一条“当前变量计划”结论，减少上下寻找

代码入口 renderInspector / renderRows / renderFooter。保持现有表格列数、元素密度与三值对照。不要把“待应用输入”改名为“待写入”，匹配与编辑状态继续分开。

在 inspecthead 下、当前选定值上方插入紧凑计划条：左侧显示 `Path · 用户` 的本次计划结论；右侧仅保留一个轻量动作，例如有问题时 `查看保留原因`（展开并定位内部说明）、正常时 `查看完整预览`（使用原有当前确认范围，不能偷偷缩成单变量）。无变化用中性灰色；真实变更用绿；保护说明用琥珀；非法上下文使用现有错误色。

原 compareSummary 中逐项操作说明仍保留，但避免在计划条和页脚完整重复。将 `恢复编辑` 改为更明确的 `恢复本次选定值编辑` 或提供同义的 aria-label，说明这是恢复输入，区别于“撤销预览”。

表格每行变量名称或状态处增加一个明确的 `查看对照`可聚焦按钮（可复用变量名称作为按钮），让键盘用户能只选择对照而不必进入输入框或来源选择。点击后更新 focusedVariable、展开对照、滚动到对照标题；不调用输入 setter。表格原行点击行为可保留。

验收：Tab可以选中并打开每个变量的三值对照；点击查看不修改值来源或 dirty；600px能发现对照入口且不新增整页横向滚动；仅看未匹配筛选下当前变量隐藏时行为明确且不误改其他变量；输入过程中不重复抢焦点。

## 4. P1：预览布局、刷新焦点与窄屏收尾

现有已实现焦点圈、Tab trap、Escape与原触发按钮还焦，不要重建一套。重点修补新增摘要/跳转/返回动作之后的可达性。

预览采用三段 flex 布局：固定标题与简短状态、唯一可滚动 body、固定动作 footer。避免 .dialog 与 .dialogbody 同时滚动。顶部索引可在 body 内，超过少数目标时不要把可用高度全部占完。600px横向尺寸保持现有 max 96vw，body不横溢；标题/作用域允许自然换行；before/after沿用700px断点上下排列；footer可两行，说明在上、按钮在下且右对齐。最短测试高度至少600×640，常规600×800与1360×900。

刷新保留已打开原文与合理滚动位置；用 targetKey+role/relatedKey恢复焦点，而不只依赖旧索引。聚焦返回检查、原文summary或索引时发生自动刷新，也不能让焦点掉到body。找不到原控件时落到预览标题/状态，而非页面背景。review动作保持单独且不写；状态 role=status 温和播报版本变更，不对整个长 Path 使用高频live播报。

视觉 token：复用 --green/#286c51（操作与可执行）、--ink/#24382d（结论）、--sub/#617568（辅助）；新增审阅中性底 #f5f7f5、保留警示底 #fff8eb/边 #e5c991/文字 #805c25，错误复用现有红色。状态带圆角8px、边1px、内边12–14px；标题14px/650，说明12px/1.55；指标数字等宽，禁止大型KPI卡、发光或持续动画。保留现有新增/删除/移动token色，不重新赋色。

验收：600px/宽屏截图；Tab/Shift+Tab不越出弹窗；索引Enter跳转并使标题可见；Escape还焦；刷新时开着原文、焦点位于summary/索引/token三种情况均保留合理焦点；reduced-motion下无新增动画；至少手动截图验证不溢出、不遮挡。

## 实施边界与顺序

先做1+2，验证 frozen-plan 不变，再做3+4。新增只读 presentation helper可以独立函数，但不要修改 demo-plan.js、windows-elements 的序列化/Audit算法、V2或Python。所有新增统计都来自既有 plan.operations/issues/before/after；状态分类仅影响文案与导航，不能影响 eligibility 或确认验证。资源修改后更新现有内容hash查询串。

建议验收除了全套npm test，补一组真正浏览器流程：正常追加、无变化、重复保护、共享保护、continuity保护、批量冲突、append限制、相关刷新两步确认、无关刷新不失效、600px键盘导航。测试应验证交互效果和冻结内容，而非只匹配静态文案。

本轮不做：新主题、再一次侧栏翻新、自动解决冲突、一键删除受保护项、自动切换操作模式、真实注册表、后台轮询、TOML/持久身份扩展、将UI汇总倒灌业务计划。
