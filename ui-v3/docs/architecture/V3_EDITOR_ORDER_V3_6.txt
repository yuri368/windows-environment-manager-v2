【架构顾问 → Codex】

批准启动 V3.6。 这五项反馈主要涉及元素编辑器的视觉顺序、建议采纳状态和删除痕迹，不需要调整 V3.5 已经稳定的业务规则。

我核对了 V3.5 的 windows-elements.js。当前 rowDisplayOrder() 每次根据原始位置重新安排幽灵行，而 move() 只操作 live rows。两套排序依据确实会造成编号和视觉位置不一致。

你的 displayOrder 方案可以解决这个问题，但需要明确：它负责可见行顺序，而不是第二套环境变量数据。

另外，建议采纳后的绿色状态可以增加一个会话级来源映射。只要它不参与 DemoPlan 的业务决策，也不会形成新的业务状态系统。

下面是本轮最终契约。

写作
V3.6 元素编辑器顺序与建议切换契约

状态：批准实施
基线：V3.5
范围：本轮五项 GUI 反馈

一、基本原则

元素编辑器保留三类数据：

1. originalRows

打开编辑器时的原始元素，保持不可变。

2. session.rows

当前真实参与本次编辑的 live rows。

唯一决定：

最终元素内容。

最终序列化顺序。

ChangePlan。

Audit。

Apply。

History。

3. displayOrder

仅表示界面中所有可见元素的排列顺序，包括：

存活的原始元素。

新增元素。

已移除的原始元素幽灵。

幽灵行不参与真实序列化。

另允许存在轻量的 adoptionMap，只记录本次通过建议 ＋ 按钮创建的元素身份。

不得为上述内容额外建立第二个业务 ChangePlan。

二、displayOrder 最小结构

推荐使用：

displayOrder: ElementId[]

例如：

原始元素：

A（id=1）

B（id=2）

C（id=3）

D（id=4）

删除 B 后：

live rows：1、3、4

displayOrder：1、2、3、4

其中 id=2 被渲染成幽灵行。

移动幽灵 B 至底部：

live rows：1、3、4

displayOrder：1、3、4、2

最终字符串仍为：

A;C;D

必须维持的不变量

displayOrder 中的 ID 不重复。

每个 live row ID 必须在 displayOrder 中出现一次。

每个原始 ID 都保留在 displayOrder 中，即使已经被删除。

本次新增又删除的 ID 从 displayOrder 移除。

不允许显示未知 ID。

live rows 顺序始终等于 displayOrder 过滤幽灵后的顺序。

推荐每次排序后统一同步：

session.rows = displayOrder.filter(isLive).map(getLiveRow)

这里仅重排已有 live row 对象，不重新创建 ID，也不改变元素内容。

三、统一编号

所有可见行按照 displayOrder 使用连续编号。

例如：

A

B（已移除）

C

D

不再混用 live index 和 original index。

幽灵行可以通过 tooltip 保留：

“原始位置：第 2 项”。

原始位置只是辅助信息，不显示为当前列表编号。

elementTotal 继续只统计 live rows。

四、幽灵行移动

幽灵行允许使用 ↑、↓。

操作规则：

每次与 displayOrder 中相邻的可见行交换位置。

可以跨越 live row 和其他幽灵行。

不改变幽灵的原始稳定 ID。

不将幽灵重新加入 live rows。

不生成实际 MOVE 操作。

不修改最终字符串。

不产生 History 操作。

幽灵行仍然：

不可编辑。

不可删除第二次。

不可作为普通输入。

不参与序列化。

上下移动按钮的辅助说明应明确：

“仅调整已移除元素的展示位置”。

live 元素移动

live 元素的 ↑、↓ 也按照 displayOrder 的相邻位置移动。

移动完成后重新过滤出 live rows。

只有 live 元素之间的真实相对顺序发生变化时，才允许由现有 Audit 生成 MOVE。

例如：

displayOrder：

A、B（幽灵）、C

将 A 下移一次：

B（幽灵）、A、C

实际 live 顺序仍是 A、C，因此不生成业务 MOVE。

再将 A 下移一次：

B（幽灵）、C、A

实际 live 顺序变为 C、A，此时才产生业务 MOVE。

拖拽

保留 live row 拖拽。

拖拽应更新 displayOrder，允许以幽灵行为放置目标，默认插入到目标行之前。

幽灵本身不要求支持拖动。

拖拽结束后统一同步 live rows。

禁止拖拽事件继续绕开 displayOrder，直接维护另一套顺序。

五、建议追加的采纳来源

新增：

adoptionMap

最小记录：

suggestionIndex

elementId

adoptedRaw

mode

仅用于记住：

“这个元素是由哪一次建议 ＋ 操作创建的”。

不需要额外保存完整元素对象，也不需要持久化。

未采纳

卡片正常显示：

E [＋]

状态：建议追加。

已采纳

点击 ＋：

创建新的 live row。

分配稳定 ID。

按原有头部/尾部模式插入 displayOrder。

同步 live rows。

在 adoptionMap 中记录来源。

重新生成 session.plan。

卡片不消失，变为绿色：

E [✓]

按钮：

aria-pressed="true"

提示“撤销本次采纳”

不再显示“建议追加”

绿色表示已加入本次编辑，不代表 Windows 已执行。

再次点击

根据 adoptionMap 保存的 elementId：

找到确切的已采纳元素。

检查它仍然是对应的 live row。

检查内容未被手动改写。

从 live rows 中移除该 ID。

从 displayOrder 中移除该 ID。

清除 adoptionMap 记录。

重新生成计划和候选展示。

不得按元素字符串删除。

不得删除其他同值元素。

不得误删用户手动新增的行。

六、已采纳元素被再次编辑

这是本轮最重要的边界。

情况 A：手动移动已采纳元素

保留采纳来源。

例如：

建议加入 E，用户随后将 E 移到另一个位置。

只要：

elementId 没变。

raw 没变。

卡片仍然是绿色已采纳。

再次点击 ✓，仍允许撤销该确切 ID。

情况 B：手动修改已采纳元素内容

例如：

建议 E → 已采纳 E → 用户改成 F。

裁定：

立即解除采纳来源关系，但保留用户修改后的 live row。

原因：该行已经成为用户明确编辑的内容，不应允许旧建议按钮继续把它删除。

具体行为：

清除该 ID 在 adoptionMap 中的记录。

保留该行和稳定 ID。

重新计算建议是否仍然缺失。

如 E 仍然缺失，E 恢复为普通“建议追加”。

如果 E 已被其他 live row 满足，则不重复建议。

即使用户稍后把 F 改回 E，也不自动恢复绿色已采纳状态。

只有重新点击 ＋，才建立新的采纳关系。

情况 C：手动删除已采纳元素

删除对应 live row。

从 displayOrder 移除新增 ID。

清除 adoptionMap。

如建议重新缺失，则恢复未采纳建议。

因为这是本次新增的元素，不产生原始幽灵行。

情况 D：其他元素已满足同一建议

例如建议 E，但用户已经手动添加 E。

不显示绿色“已采纳”。

因为它不是通过该建议按钮创建的。

应按现有候选规则隐藏不再缺失的建议。

情况 E：重复 Desired

重复目标只保留实际需要的一份建议。

采纳来源与明确 suggestionIndex 绑定。

不得出现多个绿色采纳卡片对应同一个实际元素的情况。

七、建议卡片渲染

建议区显示内容由两部分合并：

当前仍未满足的建议。

adoptionMap 中仍有效的已采纳建议。

按原始建议顺序稳定排列。

已采纳建议不得因为当前 missing 计算结果变为空而立即消失。

建议状态只能由明确的 adoptionMap 和当前 live rows 确认。

不能通过“现在存在 E”反向推断“E 已采纳”。

建议删除部分继续遵守 V3.4 契约，本轮只修改建议追加的切换行为。

八、还原、取消与失效
还原本次编辑

恢复原始 live rows。

恢复 displayOrder 为原始 ID 顺序。

清空 adoptionMap。

幽灵行消失。

绿色已采纳卡片恢复为正常建议。

session.plan 回到无变化。

取消

丢弃当前 session，包括 displayOrder 和 adoptionMap。

不修改演示 Windows 快照。

应用

只使用 session.plan。

adoptionMap 与 displayOrder 不进入执行器或历史记录。

应用前仍按原有规则校验快照。

方案建议失效

禁用 ＋/✓ 切换。

不得继续使用旧方案候选执行新的采纳动作。

现有独立手动编辑能力保持不变。

Special / Whole

不启用普通元素建议切换，也不展示不适用的幽灵排序功能。

九、编辑后对照排序

elementOriginal：

始终保持原始快照顺序。

elementPreview：

按 displayOrder 渲染完整的编辑后可视序列。

live 元素：正常显示。

删除的原始元素：在当前位置显示幽灵 token。

新增元素：在实际位置显示。

删除元素不再集中堆到独立的“已删除”区域。

幽灵 token 使用删除线和删除视觉效果。

elementSerialized：

只能根据 session.plan.after / live rows 表示真实结果。

不能从包含幽灵的可视序列重新拼接。

当最后一个 live 元素被删除：

幽灵仍可见。

真正 After 为变量不存在。

删除结果语义不改变。

十、删除幽灵的视觉强化

允许采用更明显的静态视觉：

对比度更清楚的斜线纹理。

虚线或断裂式边框。

局部切角或裂缝装饰。

稍明显的删除线。

但必须满足：

不修改真实文本。

不向字符串插入斜杠。

不遮挡长路径中的字符。

hover/focus 联动仍清楚。

颜色不成为唯一状态说明。

窄屏不横向溢出。

优先通过 CSS 伪元素实现。

不增加持续闪烁、扫描、流动条纹等动画。

如果使用短暂状态过渡，应遵守 prefers-reduced-motion。

十一、验收重点

live 与 ghost 编号连续、唯一。

ghost 上下移动不改变 plan.after。

live 跨 ghost 移动，只在 live 相对顺序变化时生成 MOVE。

拖拽 live 跨 ghost 与按钮排序一致。

原始重复元素仍按稳定 ID 区分。

编辑后对照与可见 displayOrder 一致。

幽灵不会污染真实序列化、History 或 Apply。

采纳 ＋ 后卡片保留并变绿。

点击绿色 ✓ 仅撤销对应稳定 ID。

移动已采纳元素后仍可撤销。

修改已采纳元素后自动解除来源，保留手动修改。

手动删除已采纳元素后建议恢复。

手动新增同值元素不冒充已采纳。

还原清空显示排序与采纳来源。

无效方案不能操作旧建议。

原 V3.5 增删、替换、空元素、重复、历史回归保持通过。

十二、本轮边界

允许新增的会话数据仅为：

displayOrder

adoptionMap

不新增第二套计划生成器。

不修改：

DemoPlan。

temp.html 的应用与历史流程。

Windows 快照结构。

V3.2 增删规则。

V3.3 三值对照核心。

V3.4 建议与实际编辑的边界。

不接入真实注册表，不引入框架，不修改 V2，不合并 main，不发布 Release。

最终原则：视觉顺序可以独立变化，真实操作仍由 live rows 决定；采纳可以撤销，但只能撤销那条被明确采纳的元素。

补充两点实施要求

第一，displayOrder 不应每次重新推算。 V3.5 的幽灵行锚点算法适合初始展示，却不适合用户反复上下移动。V3.6 初始化一次后，应由明确的排序操作维护它，否则移动完下一次刷新又漂回去了。

第二，adoptionMap 不应该进入 Audit。 采纳 E 和手动新增 E，实际应用结果都只是新增 E，来源只影响编辑器里的绿色状态和撤销按钮，不影响环境变量操作语义。

裁定：Codex 可以开始 V3.6 实施。 严格限定上述五点，完成后提交源码、回归测试与对应 GUI 截图，再进行下一轮审查。
