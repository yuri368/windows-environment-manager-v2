确认最新理解。你提出的方向符合负责人这次明确的新要求，可以替代 V3.1 对普通选定值编辑“只追加、不删除”的限制。

但有一处必须严格区分：

不猜测替换关系，不等于不能执行删除。

这次删除的依据不是推测 C → E，而是用户明确从原选定值中移除了 C，并且 C 在编辑开始前确实匹配 Windows 当前值。新增 E、F 则是独立操作。

因此：

A;B;C → 选定 A;B;E;F：删除符合条件的 C，追加 E、F。

不生成 C → E 的 REPLACE。

不再把所有普通编辑强行解释成只追加。

“待删除”和“待追加”必须与最终实际操作一一对应。

不过，匹配成功只能证明元素存在，不能证明这个元素归某个应用独占。因此重复元素和共享 PATH 必须采用保守删除规则，否则看似不猜替换，实际上又开始猜元素所有权了。

我同意采用你的基线方案，下面给出本轮可直接执行的最终契约。

写作
V3.2 选定值编辑差异契约

状态：架构裁定，允许实施
适用范围：V3 浏览器演示
优先级：覆盖 V3.1 中与本次选定值编辑相冲突的规则

1. 核心定义

选定值编辑由四个独立事实构成：

ActualSnapshot：编辑开始时的 Windows 状态。

OriginalSelected：编辑开始前的原选定值。

MatchedBaseline：原选定值中已匹配的元素及实际元素候选。

CurrentSelected：用户修改后的当前选定值。

计划生成器根据这些事实生成确定的 REMOVE 和 ADD，不推测 REPLACE。

关键区别

普通 append 应用，没有选定值编辑基线时，仍执行原有的只追加规则。

发生有效的选定值编辑时，允许撤销原来已匹配、现在不再需要、且安全可删除的元素，再追加新的缺失元素。

该规则不代表 append 模式今后可以任意删除 Windows 元素。

2. 基线捕获
捕获时机

首次真正修改某个选定值之前捕获。

应在 setSelectedValue 改写值之前执行，而不是用户仅获得输入框焦点时捕获。

基线至少记录：

应用 ID。

方案 ID。

scope 和 canonicalName。

mode 和 special。

原选定值 raw。

Windows exists/raw/type/revision。

原选定有效元素的 normalized 值。

哪些原选定元素当时已匹配。

与已匹配值相符的实际元素位置、原始字符串及出现次数。

注意：MatchedBaseline 可以记录实际候选位置，但不能将普通文本匹配提升为稳定元素身份。

基线稳定性

同一次编辑会话中：

连续输入不刷新基线。

不因为中间输入变成空字符串而刷新。

不因为工作台重新渲染而刷新。

不因为用户反复输入 A→B→C 而刷新。

Undo/Redo 使用同一基线重新计算当前计划。

基线是只读数据。

3. 基线清理

以下情况清理：

计划成功应用，并完成演示数据验证。

用户明确执行“恢复编辑”，回到编辑前选定值。

切换应用或方案，且原编辑会话明确结束。

重置演示。

以下情况不清理：

取消预览。

关闭预览。

Escape 退出预览。

仅刷新 UI。

计划因为快照过期而被拒绝。

如果编辑来源、scope、mode 或 special 改变，原基线不得继续用于新上下文。应先结束或重建相应编辑会话，而不是混用两个上下文。

4. 删除规则

对每个原已匹配的 normalized 目标元素，依次检查：

它存在于 MatchedBaseline。

它已不在 CurrentSelected 的有效目标集合中。

原 Windows 快照中存在对应实际元素。

对应实际 occurrence 可以无歧义地确定。

没有其他受保护方案仍然需要该元素。

当前快照与基线仍然一致。

全部满足，才生成 REMOVE。

不满足时，不生成可执行 REMOVE。

特别注意：

删除依据是“原来明确选中且匹配，现在明确不再选中”，而不是寻找哪个新元素与旧元素相似。

普通字符串编辑不生成 C→E、B→F 等配对关系。

删除方式

使用已确认的实际元素位置处理原始元素列表，不能对 raw 直接执行全局字符串替换。

删除后保留其他元素的原始文本、重复项、空元素和相对顺序。

删除最后一个有效元素时，不得擅自混淆“变量不存在”和“存在但为空”。边界行为必须与已有删除语义一致，并单独测试。

5. 新增规则

CurrentSelected 中的非空目标元素，如果当前有效结果尚未包含，则生成 ADD。

规则：

trim 后比较。

大小写敏感。

不展开 %VARIABLE%。

保留新增目标的首次原始写法。

重复目标按原有规则计入匹配比例。

相同 normalized 值最多生成一个实际 ADD。

+append 前置新增项。

-append 后置新增项。

普通 append 继续遵守已有排序确认限制。

原选定值中曾经缺失，但现在已被用户删掉的候选，不产生 REMOVE，也不继续产生 ADD。

6. 预期案例
Actual	原 Selected	新 Selected	最终变化
A;B;C	A;B;C;D	A;B;E;F	REMOVE C，ADD E/F
A;B;C	A;B;C;D	E;F;G;H	REMOVE A/B/C，ADD E/F/G/H
X;A;B;C;Y	A;B;C	A;E	REMOVE B/C，ADD E，保留 X/Y
A;B;C	D	E	ADD E，保留 A/B/C
A;B;C	A;B;C	A;B;C	无变化

这些案例均不生成推测 REPLACE。

结果必须由同一个冻结 ChangePlan 提供给工作台、对照、预览、演示应用和历史。

7. 重复 occurrence 的处理

必须严格区分：

目标值是否存在。

Windows 中有几个相同元素。

哪个具体 occurrence 获得了删除授权。

例如：

Actual：A;B;B;C

原 Selected：A;B;C

新 Selected：A;C

原 B 确实匹配，但 Windows 有两个 B。

由于无法证明哪个 B 属于当前方案，默认不得自动选择一个删除，更不能一口气删除所有 B。

此时：

记录 B 已从选定值移除。

显示“删除需确认”或“存在重复，未自动删除”。

不将未确认删除写入 operations。

实际 after 中保留两个 B。

需要删除时，由用户通过现有元素编辑器明确选择 occurrence。

不新增自动推测 occurrence 的算法。

8. 共享元素保护

对符合删除条件的元素，还需要进行共享依赖检查。

最小保护范围：

当前同一目标变量下，其他仍有效的选定方案。

同批次中其他应用的最终目标值。

V2 共享撤销规则原本要求保护的未勾选应用及其方案。

只要存在受保护的共享依赖，就不能静默 REMOVE。

默认：

保留共享元素。

记录共享保留原因。

不给它贴可执行的“待删除”标签。

如果已有共享冲突确认流程可复用，则按原有明确确认机制处理；本轮不得为了实现这一功能重造大型冲突管理界面。

系统只能判断已管理配置中的共享关系，不能声称能够识别机器上所有软件的元素所有权。

9. 同目标批量计划

同一 scope + canonicalName 必须统一规划。

流程：

从同一个目标快照出发。

收集所有参与批量操作的当前目标和编辑基线。

先计算各方案仍然需要保留的元素。

汇总符合条件的 REMOVE。

对共享、重复和冲突进行过滤。

按现有模式与顺序规则生成 ADD。

生成该目标唯一确定的最终 after。

不能让应用 A 计划删除 B，同时让应用 C 的目标仍然要求 B，却通过先删后加掩盖冲突。

如果同一目标存在无法协调的 replace、排序或删除冲突：

阻止受影响操作。

展示冲突原因。

不隐式选择某个应用优先。

不偷偷改变已有批量应用顺序规则。

如果两个应用请求相同的 ADD，最终只写入一次。

10. 快照失效与用户处理

计划生成时冻结：

targetKey。

exists/raw/type/revision。

原选定值及编辑基线。

当前选定值。

mode/special。

相关批量方案的有效目标。

点击确认前重新验证对应目标。

相关快照未变化

可以继续演示执行冻结计划。

仅无关目标变化

不使当前计划失效。

相关目标发生变化

必须：

拒绝旧计划。

保留用户当前输入，不自动覆盖。

显示原快照与新快照发生的变化。

提供明确重新检测及重新预览流程。

用户确认重新建立基线后，才基于新快照重新计算。

新计划必须重新确认，不自动执行。

重建时保留原选定值和当前编辑值，但重新确认原选定值在新快照中的已匹配范围。

不得在后台悄悄刷新 MatchedBaseline。

失效的计划不产生成功历史。

11. 标签与执行严格一致

定义：

待删除：冻结 ChangePlan 中存在确定、可执行的 REMOVE。

待追加：冻结 ChangePlan 中存在确定、可执行的 ADD。

删除需确认：检测到删除意图，但 occurrence、共享依赖或其他约束不允许自动删除。

选定值已修改：仅说明用户编辑了目标值，不代表已经执行。

整体待替换：replace/special 模式对整个变量值执行替换。

禁止普通输入根据相邻位置、字符串相似度或编辑顺序猜测 REPLACE。

禁止“待删除”只存在于 UI 标签里，实际 ChangePlan 不删除。

禁止“待追加”已经取消，却仍出现在元素编辑器候选中。

现有 Windows 元素编辑器的显式稳定 ID REPLACE 能力保持原样，与普通选定值编辑产生的 REMOVE+ADD 区分。

12. 本轮实施范围

只修改必要的：

编辑基线捕获和生命周期。

DemoPlan 的编辑场景增删计算。

当前统一 ViewModel 的标签投影。

预览、演示应用和历史的计划消费。

对应回归测试。

保留：

现有紧凑 UI。

原生 HTML/CSS/JS。

既有演示数据。

无额外框架。

无真实注册表接入。

无 V2 业务核心迁移。

无大规模目录重构。

优先复用现有 DemoPlan，不得再建立第二套实际增删计算器。

13. 验收条件

以上五组确定性示例必须全部通过。

还需要覆盖：

Windows 重复 occurrence 不自动误删。

同目标共享元素默认保留。

一个缺失目标从 D 改为 E 时不生成 DELETE D。

选定值改回原值后计划恢复无变化。

连续编辑不刷新基线。

取消预览不丢失编辑基线。

相关快照过期拒绝执行。

无关快照变化不影响当前计划。

用户明确删除并追加后的预览、演示实际值与历史一致。

全部满足后，才认为本轮需求完成。

最终裁定：不猜替换关系；以冻结的已匹配基线确定可安全撤销的旧元素，以当前选定值确定需要新增的元素。无法确认的删除不执行。

还有一项实施提醒：这次属于规则层的真实变更，不只是更换“待修改”标签。原来通过的 235 项测试只能作为回归基线，必须新增覆盖删除行为的测试。

Codex 可以按这份契约开始最小修改。当前不授权接入 Windows 注册表、不授权整体重构，也不授权合并主分支。
