二、问题 1：区分“手动新增”与“方案建议新增”
当前问题

用户通过“＋新增元素”按钮创建的新元素，使用普通的“新增”状态标记。

但方案建议中的“＋采纳”同样会新增元素，两种来源在编辑器中缺少明确区分。

最终需求

来源 A：用户手动创建

标记文字改为“手动新增”。

使用现有新增色系，但颜色与普通“新增”存在细微区别。

可使用略有不同的浅背景、边框或图标。

不使用突兀的大面积强调色。

删除后直接从列表消失，不产生幽灵行。

来源 B：采纳方案建议

继续显示“新增”。

建议卡片仍显示“已采纳”状态。

继续保留原有绿色采纳反馈。

与手动新增在视觉上能够区分。

技术要求

新增来源属于 UI 会话元数据，不改变 DemoPlan 的 ADD 语义。

手动新增、方案采纳新增均属于真实 live row。

两种来源的 Audit/ChangePlan 操作仍是 ADD。

新增来源必须在后续修改、移动、重绘后保持正确。

注意：adoptionMap 可能在用户手动编辑已采纳元素后清除，因此不能单纯依赖它的当前状态判断元素最初来源。

可以使用最小化的会话级来源记录，不引入新的业务模型。

UI 来源标记不得写入 WindowsSnapshot、ChangePlan 或 History。

验收

手动新增显示“手动新增”。

建议采纳新增显示“新增”。

两种标记颜色有细微区别。

元素移动、编辑后来源不混淆。

手动新增后删除直接消失。

新增再删除且没有其他修改时，Apply 禁用。

不出现虚假的 REMOVE 操作。

三、问题 2：幽灵行显示原始值，而不是删除前的最新值
当前问题

无论原始元素是否为空，只要用户修改后再删除，幽灵行仍然显示最初的 Windows 值。

例如：

普通元素

原始值：ABC

用户修改：ABC123

点击删除后：

当前幽灵行显示：ABC

点击取消删除后恢复：ABC123

原始空元素

原始值：""

用户修改：TEST

点击删除后：

当前幽灵行显示：“（空元素）”

点击取消删除后恢复：TEST

此行为会让用户误以为先前的修改已经丢失。

已知原因

当前源码的 deletedDrafts 已保存删除前的最新草稿。

但幽灵行的展示仍读取 originalById，没有使用最新草稿。

因此这是一个展示投影问题，不需要改变 ChangePlan。

最终需求

对所有原始元素统一处理：

删除时保存该元素最后一次编辑内容。

幽灵行显示删除瞬间的实际草稿值。

未修改的元素显示原始值。

原始空元素修改后，幽灵行不再错误显示“（空元素）”。

“打开时的值”区域始终显示最初 Windows 快照。

点击普通幽灵行“取消删除”，恢复最新草稿。

恢复后保留稳定 ID 和幽灵行当前 displayOrder 位置。

再次修改、删除时显示最新一次删除前的值。

删除幽灵不进入实际序列化、ChangePlan、Audit 或 History。

重要边界

此前 V3.7 中的绿色“建议删除”采纳撤销，仍然遵守原有规则：

点击绿色 ✓ 撤销建议删除时，恢复原始值。

普通幽灵行的“取消删除”恢复最后编辑草稿。

这两种操作不能混淆。

原始快照和删除前草稿必须继续分开保存。

验收

非空元素：修改 → 删除 → 幽灵显示修改值 → 恢复。

空元素：修改 → 删除 → 幽灵显示修改值 → 恢复。

重复值：只操作指定 stable ID。

修改 → 删除 → 恢复 → 再修改 → 再删除。

删除后移动幽灵位置再恢复。

原始对照不随草稿改变。

特殊字符串和原有换行不被错误清理。

Apply/History 仍使用真实 live rows 和既有操作计划。

四、问题 3：统一普通行与幽灵行的操作按钮
当前问题

普通行的按钮顺序是：

↑  ↓  删除

幽灵行的按钮顺序是：

取消删除  ↑  ↓

幽灵行的“取消删除”按钮过宽，导致上移、下移按钮与普通行不对齐，视觉上显得突兀。

最终需求

普通行与幽灵行使用完全相同的操作栏布局。

统一为三个操作位置：

上移  下移  删除/恢复

第三个按钮根据元素状态切换。

状态 A：普通元素

图标：现有垃圾桶图标。

功能：删除当前元素。

使用柔和的红色系。

Hover 时可以显示浅红色背景或边框。

删除原始元素时，保留 Claude 现有碎裂、消散动画。

本次新增元素删除后直接消失。

状态 B：幽灵元素

图标：撤销、恢复箭头。

功能：取消本次删除。

使用柔和的绿色或青绿色。

Hover 时显示浅绿色背景或边框。

可以有短暂的恢复动效，但不持续闪烁。

恢复时保留原始稳定 ID、最新草稿与当前展示位置。

统一布局规范

两种状态必须保持：

相同的按钮宽高。

相同的按钮排列顺序。

相同的间距。

相同的容器对齐方式。

相同的响应式行为。

恢复按钮不再使用长条形文字按钮，只显示图标。

必须通过 title/tooltip、aria-label 提供完整含义。

建议文案：

删除此元素。

取消删除，恢复删除前的编辑内容。

移动行为

幽灵行仍可上移、下移。

幽灵移动只调整 displayOrder，不直接产生业务 MOVE。

恢复后若实际 live 顺序变化，由既有 Audit 判断 MOVE。

不改变原有拖放行为。

验收

普通行与幽灵行的 ↑ ↓ 完全对齐。

删除/恢复图标占用相同位置。

两种状态颜色和交互反馈清晰。

不再出现宽大的“取消删除”按钮。

100%、125%、150%、200% 缩放下保持对齐。

Tab、Enter、Space 均可正常使用。

原始元素删除与恢复的业务语义不变。

保留 Claude 现有删除动画。

五、问题 4：建议按钮与匹配图标没有在圆圈内居中
当前问题

负责人发现以下图标在圆圈内明显偏上：

“采纳建议追加”的 ＋。

“采纳建议删除”的 −。

两种建议按钮采纳后显示的返回图标 ↶。

“编辑后的值 · 含删除标记”区域中，通过采纳建议追加生成的元素所显示的绿色 ✓ 图标。

表现为图标似乎漂浮在圆圈中心上方。

排查位置

重点检查：

elements-ui.css

fx-ui.css

windows-elements.js 中的图标生成结构

相关选择器包括：

.pending-add-button

.pending-remove-button

.element-match-mark

按钮的 ::before 及采纳状态样式。

排查方向

此前发现一个需要验证的可能原因：

部分按钮同时包含文字图标与 CSS ::before 绘制的图标，通过 font-size: 0 隐藏文字。

在 Grid 布局中，这可能产生额外的布局子项，影响伪元素的实际位置。

此原因尚未通过真实浏览器布局测量最终确认，不能直接视为已证实。

Codex 应首先检查：

图标容器实际尺寸。

::before 盒模型。

Grid/Flex 对齐。

伪元素是否产生额外网格行。

CSS mask 的绘制框是否居中。

SVG 图形本身的视觉重心。

不同缩放下是否有像素取整偏差。

修复原则

优先修复共同的布局原因。

不要简单为四个图标分别增加 translateY()。

只有 SVG 自身视觉中心偏移时，才允许少量光学校正。

不改变圆圈整体大小、颜色、Hover、Focus 或采纳动效。

保留 aria-label 与键盘访问能力。

不改变采纳、撤销及匹配逻辑。

验收

＋、−、↶、✓ 均在圆圈中央。

普通、Hover、Focus、已采纳状态均无明显偏移。

100%、125%、150%、200% 缩放下稳定。

采纳与撤销操作正常。

匹配图标不污染实际值。

其他同类圆形图标若存在相同问题，可做同因修复，但不扩大为整个图标系统重构。
