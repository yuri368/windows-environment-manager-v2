# Environment Manager V3 Coding Guidelines

版本：V3.0

状态：开发规范


==================================================

# 1. 开发目标


V3开发必须遵循：

简单

明确

可维护


优先级：

1. 正确架构

2. 数据一致性

3. 可测试

4. 功能完整

5. UI优化



禁止：

为了短期效果破坏长期结构。



==================================================


# 2. 修改前原则


任何代码修改前必须回答：


## 问题属于哪个层？


例如：


UI显示错误：

属于：

UI/ViewModel


不是：

修改核心规则



--------------------------------------------------


匹配错误：

属于：

Matching



--------------------------------------------------


变化判断错误：

属于：

Planning



--------------------------------------------------


执行错误：

属于：

Execution



==================================================


禁止：


为了修复UI：

修改Diff规则。


为了修复显示：

修改数据模型。



==================================================


# 3. 单一事实来源原则



系统状态来源：


WindowsSnapshot



目标来源：


SelectedConfiguration



变化来源：


ChangePlan



历史来源：


ExecutionResult



==================================================


禁止创建：

第二套状态系统。



例如禁止：


UIState:

isPending


Core:

pending



两个状态表示同一件事情。



==================================================


# 4. 禁止临时状态扩散


允许：


UI临时状态：


hover

focus

expanded



禁止：


业务状态进入UI：


isReallyModified

shouldAppend

maybeReplace



==================================================


业务状态必须来自：

Domain Model。



==================================================


# 5. 不允许UI猜测业务



错误：


if value not exists:

显示:

待追加



正确：


读取：

ChangePlan.operation.type



然后显示。



==================================================


# 6. 新增状态审核



新增字段前必须回答：


1.

它属于哪个对象？


2.

它是否已有表达？


3.

是否可以通过已有对象计算？


4.

是否会影响序列化？


5.

是否需要测试？



==================================================


如果只是：

为了方便显示


优先：

ViewModel转换。



==================================================


# 7. Diff规则保护



Diff规则属于核心资产。


修改Diff前必须：


检查：

- append
- replace
- special
- empty
- duplicate
- ordering



==================================================


禁止：

为了某个UI案例修改全局Diff。



==================================================


# 8. 新模块原则


新增模块必须说明：


职责：

输入：

输出：

依赖：



例如：


DiffEngine


输入：

Snapshot

Desired



输出：

ChangePlan



==================================================


禁止：


万能模块。


例如：


EnvironmentHelper


里面包含：

读取

比较

修改

记录

显示



==================================================


# 9. 函数设计原则



函数应该：


输入明确

输出明确



推荐：


calculateDiff(before, after)


返回：

ChangePlan



不推荐：


updateEnvironmentAndMaybeShowDialog()



==================================================


# 10. 不可变数据原则



以下对象默认不可变：


WindowsSnapshot


MatchResult


ChangePlan


ExecutionResult



原因：

避免：

A模块修改后

B模块看到不同结果。



==================================================


# 11. UI开发规则



UI修改优先：


修改：

ViewModel

↓

组件


而不是：

修改核心对象。



==================================================


UI不能：

访问：

Registry


不能：

解析：

TOML


不能：

生成：

ChangeOperation



==================================================


# 12. 测试要求



每次核心修改必须增加测试。


至少包含：


正常情况


边界情况


回归情况



==================================================


# 13. 提交规范



提交应该：

单一目的。



推荐：


fix:

修复append计划生成


feat:

增加元素编辑显示


refactor:

拆分Diff模块



==================================================


禁止：

一个提交同时：

修改UI

修改核心规则

修改数据结构



==================================================


# 14. AI协作规则



使用AI开发时：


AI负责：

代码实现


人负责：

需求判断



架构修改必须：

先讨论

后实现



==================================================


# 15. 大规模修改规则



以下情况必须重新设计：


- 修改核心数据模型

- 修改ChangePlan

- 修改执行流程

- 修改模块边界



禁止：

通过多个小补丁绕过架构讨论。



==================================================


# 16. UI反馈处理规则



用户反馈：

“这里显示不对”


处理流程：


1.

确认事实来源


2.

确认状态属于哪个模型


3.

确认是否已有数据表达


4.

修改正确层级



禁止：

直接添加显示字段。



==================================================


# 17. 判断是否需要重构



满足以下任意情况：

需要重新评估：


1.

一个状态被多个模块重复保存


2.

出现大量特殊判断


3.

UI需要知道核心规则


4.

修改一个功能影响多个无关模块



==================================================


# 18. 最终开发原则



代码应该让未来开发者容易理解。



优先：

清晰 > 巧妙


稳定 > 快速


统一 > 特殊



==================================================
