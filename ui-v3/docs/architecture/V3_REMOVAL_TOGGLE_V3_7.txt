批准启动 V3.7。建议使用独立的 removalAdoptions: Set<ElementId>，不必改造现有 adoptionMap。 ✅

我核对了 V3.6 的 windows-elements.js。现有 adoptionMap 以建议索引关联新增行 ID，而删除建议已经通过 beforeIndex 关联原始稳定 ID。两类采纳来源不同，强行合并反而需要额外的类型判断。

你的方案符合轻量化原则。不过有一条关键限制：恢复删除采纳必须恢复那个原始 ID，而不是撤销所有同值元素的删除，也不是创建新的替代元素。

写作
V3.7 建议删除双向采纳契约

状态：批准实施
基线：V3.6
范围：仅补齐建议删除的采纳与撤销

一、最小状态设计

保留：

originalRows：不可变原始元素。

session.rows：实际参与编辑的元素。

displayOrder：包含 live 与 ghost 的显示顺序。

adoptionMap：原有追加建议采纳来源。

新增：

removalAdoptions: Set<ElementId>

只记录用户通过方案建议区的 − 按钮明确采纳删除的原始元素 ID。

不记录手动删除的 ID。

不保存元素文本、位置或完整对象。

不进入 DemoPlan、Audit、Apply、History。

二、删除建议的两种状态
尚未采纳

显示：

%MAVEN_HOME%\bin  [−]

标签：

建议删除

点击 −：

重新验证当前按钮身份。

验证 selectionPlan 有效。

验证 beforeIndex 指向的原始稳定 ID。

验证对应 live row 仍然存在且内容等于原始建议值。

将原始 ID 加入 removalAdoptions。

使用现有 removeLiveRow 移除 live row。

保留 displayOrder 中的原始 ID，形成 ghost。

重新生成 session.plan 和界面。

此时只是采纳到编辑列表，并未修改 Windows 快照。

已采纳

卡片继续显示原始建议元素。

绿色状态：

已采纳删除

按钮变为：

✓

属性：

aria-pressed="true"

辅助说明：

“撤销本次建议删除，恢复原始元素”。

已采纳的建议不能因为对应 live row 已经不存在而从建议区消失。

三、撤销采纳删除

点击绿色 ✓：

确认该建议对应的原始 ID 位于 removalAdoptions。

确认该 ID 属于 originalRows。

确认该 ID 目前不在 session.rows。

从 originalRows 取得该 ID 的原始 raw。

使用原 ID 重新创建 live row。

保留 displayOrder 中该 ID 的当前位置。

根据 displayOrder 重新同步 live rows。

从 removalAdoptions 删除该 ID。

重新生成 session.plan、建议区和编辑后对照。

不得重新分配 ID。

不得按文本寻找替代行。

不得自动删除其他同值元素。

不得撤销当前会话中的其他编辑。

四、恢复位置

恢复位置以 ghost 当前所在的 displayOrder 位置为准，而不是原始 beforeIndex。

示例：

原始：

A、B、C、D

采纳删除 B：

A、B（ghost）、C、D

随后将 B（ghost）下移：

A、C、B（ghost）、D

点击绿色 ✓：

A、C、B、D

最终 live rows：

A、C、B、D

因此恢复 B 后，业务计划可能同时存在：

原 B 的删除操作消失。

B 与其他存活原始元素的相对顺序变化，产生实际 MOVE。

这是符合规则的。

ghost 移动本身不生成 MOVE；恢复后实际 live 顺序发生改变，才由现有 Audit 判断 MOVE。

不得因为要消除 MOVE 就偷偷将恢复的 B 移回原始位置。

五、同值元素边界

例如：

原始：

A、B、C

用户通过建议删除 B，随后手动新增一个 B。

显示：

原始 B：ghost，具有已采纳删除来源。

新增 B：新的 live ID。

点击绿色 ✓ 后：

只恢复原始 B。

手动新增的 B 保持不变。

两个 B 可以同时存在。

显示原有重复提示。

session.plan 按实际稳定身份计算结果。

不能因为值相同就认为原始删除已经被撤销。

手动删除

用户直接点击普通元素行的删除按钮：

形成 ghost。

不写入 removalAdoptions。

不生成绿色已采纳删除卡片。

已被手动删除的元素不能冒充建议采纳。

六、建议区投影

删除建议区合并两个来源：

未采纳建议

来自当前有效 selectionPlan 中、仍具有明确可采纳对象的 REMOVE。

已采纳建议

来自 removalAdoptions 中仍然有效的原始 ID。

按照原始 beforeIndex 排序，避免卡片在采纳前后跳动。

每个原始 ID 最多显示一张卡片。

不得同时显示同一个元素的“建议删除”和“已采纳删除”。

未采纳建议消失的原因必须是其当前条件不再成立，而不是简单因为找不到 live row。

已采纳状态由 removalAdoptions 确认，不根据 ghost 外观推断。

七、异常与来源清理
手动移动 ghost

保留 removalAdoptions。

绿色 ✓ 继续有效。

撤销采纳后修改原始行

来源已在撤销时清理。

之后按现有建议资格重新计算。

如果原始行已改写，不得继续提供针对旧值的确定删除按钮。

还原本次编辑

恢复 originalRows。

重置 displayOrder。

清空 adoptionMap。

清空 removalAdoptions。

恢复未采纳建议。

取消

丢弃当前会话和两类采纳来源。

Windows 演示快照不变。

Apply

只执行 session.plan。

removalAdoptions 不进入历史。

建议计划失效

不允许新采纳删除。

不允许使用过期绿色按钮继续操作建议。

显示已有“需要重新检测”提示。

独立手动编辑能力保持不变。

用户仍可通过“还原本次编辑”恢复整个会话。

防止旧按钮误操作

沿用 V3.6 的按钮身份校验。

操作前还必须验证：

当前 session。

当前建议索引。

对应原始 ID。

当前 removalAdoptions 状态。

live/ghost 状态是否与按钮所声明的状态一致。

验证失败时不修改 session.rows、displayOrder 或来源集合。

八、UI 文案

未采纳：

建议删除  [−]

已采纳：

已采纳删除  [✓]

建议区说明调整为：

“点击 − 或 ＋ 采纳方案建议；绿色 ✓ 可以撤销对应采纳。所有变化仅作用于本次编辑，确认应用前不会写入 Windows。”

ghost 行继续使用：

“本次编辑已移除”。

不把绿色 ✓ 解释成 Windows 已经删除。

九、验收测试

至少覆盖：

点击 − 后卡片保留，变绿 ✓。

再点击 ✓，原始 ID 恢复，卡片回到建议删除。

ghost 移动后恢复，使用当前位置。

恢复产生实际 live 顺序变化时，MOVE 由 Audit 正常计算。

手动删除不会显示已采纳状态。

同值手动新增不影响原始 ID 的精确恢复。

重复原始元素只恢复被采纳删除的 occurrence。

还原清空删除与追加两类采纳来源。

取消不改变演示 Windows 快照。

只采纳删除后 Apply，历史只记录真实删除。

撤销全部采纳且无其他实际变化时，Apply 禁用。

过期建议及旧按钮不可操作。

共享保护和重复不确定删除仍不可采纳。

原有追加 ✓ 撤销功能保持不变。

displayOrder、实际结果字符串、预览和历史保持一致。

十、实施边界

只修改：

WindowsElements 的会话建议状态。

建议删除按钮切换。

候选区展示文案及样式。

对应测试与截图。

不修改：

DemoPlan。

temp.html 的应用、快照和历史逻辑。

V3.2 至 V3.6 的核心业务规则。

原有追加建议的行为。

不引入框架，不接入注册表，不修改 V2，不合并 main，不发布 Release。

最终原则：采纳删除记住原始身份，撤销采纳恢复原始身份；同值不是同一个元素。

最终裁定

removalAdoptions 使用 Set 是合理的，不需要为了表面上的“统一”重构现有追加 adoptionMap。

这一轮唯一需要特别测试的是：把删除 ghost 移动到新位置后，再通过绿色 ✓ 恢复。这时真实顺序可能改变，不能错误地保证恢复操作一定是零变化。

Codex 可以开始 V3.7 的最小实施。 完成后提交源码、回归测试及 Chrome 截图，再按本契约复核。
