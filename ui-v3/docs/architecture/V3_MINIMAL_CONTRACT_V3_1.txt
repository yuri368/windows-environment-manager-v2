V3 最小执行契约与架构冲突裁定

版本：V3.1 Draft
适用范围：当前 V3 浏览器演示与下一阶段领域模型设计
状态：本轮开发约束，覆盖旧草案中的冲突条款

1. 总体原则

系统区分四件事：

Actual：当前 Windows 环境变量的原始状态。

Desired：用户当前选定的目标值。

SelectionChange：用户如何修改了选定值。

ChangePlan：如果确认应用，系统实际准备改变什么。

其中：

MatchResult 描述 Actual 是否满足 Desired。

SelectionChange 描述用户编辑目标值的事实。

ChangePlan 描述实际操作和最终结果。

UI 不得将 SelectionChange 解释为已经确定的 Windows 修改操作。

工作台、Windows 对照、预览和历史必须使用统一的匹配及计划计算规则。

2. “待修改”和“待追加”的最终裁定
2.1 普通字符串编辑

初始 Windows 值：

A;B;C

初始选定值：

A;B;C;D

用户修改选定值为：

A;B;E;F

可确定的事实：

A、B 继续匹配。

原选定值中的 C、D 已不在新选定值中。

新选定值出现 E、F。

Windows 当前值 A、B、C 没有改变。

允许展示：

选定值已修改

原选定值：A;B;C;D

新选定值：A;B;E;F

原选定项 C、D 不再选中

新选定项 E、F

但在 append 模式下，实际 ChangePlan 仍为：

保留 A、B、C

追加 E、F

不删除 C

不执行 C→E、F 替换

特别注意：D 已经从当前选定值中消失，因此不能继续声称 D 是待追加项。只有 D 仍包含在当前有效 Desired 中，才可能进入待追加计划。

2.2 普通输入不自动产生 Windows 替换

例如：

%PYTHON_HOME%\Scripts

改成：

%PYTHON_HOME%\Scripts1

应展示：

选定值：已编辑。

匹配结果：新元素目前缺失。

append 计划：追加 Scripts1，保留 Windows 原 Scripts。

Windows 原 Scripts：不是待修改状态。

可以显示整串前后差异，但不能给旧 Windows 元素贴上“待修改”标签。

2.3 何时允许“待修改”

仅当实际计划明确包含对已确定对象的修改时：

用户在 Windows 元素编辑器修改某个稳定 ID 的元素。

replace 模式明确执行整个变量值替换。

其中，普通元素编辑可以展示：

C → E，标记“待修改”或“替换”。

整个变量替换应展示“整体待替换”，不得伪造逐元素对应关系。

2.4 “预计修改”的处理

允许将算法推测保存在只读解释信息中，但不得：

变成可执行 REPLACE。

改写 ChangePlan 的 after 值。

给 Windows 原元素贴确定性的“待修改”标签。

改变候选按钮实际动作。

本轮不实现自动推测多对多元素替换，也不引入推测替换的 UI 按钮。

3. 待追加按钮的契约

“待追加”表示 ChangePlan 中确定的追加候选。

元素编辑器内的 ＋：

仅将单个候选加入当前编辑会话的 live rows。

+append 加入开头。

-append 加入末尾。

append 沿用当前编辑器的末尾加入行为。

不直接修改 Windows 快照。

不执行替换。

不删除旧元素。

加入后获得新的会话内稳定 ID。

取消编辑不改变原始快照。

如果用户希望实际修改旧元素，应使用现有 Windows 元素编辑入口，编辑明确的实际行并确认。

不得出现“待修改”标签旁边的按钮，实际却执行追加操作的情况。

4. 最小数据契约
TargetKey

scope：User / System。

name：原始变量名称。

canonicalName：用于查找的标准化名称。

User/System 必须严格隔离。变量名匹配遵循 Windows 不区分大小写的规则，展示时保留原名称。

WindowsSnapshot

每个目标至少包含：

targetKey

exists

raw

registryType

revision

约束：

exists=false 表示变量不存在，raw=null。

exists=true 时 raw 必须为字符串，可以是 ""。

raw 保留原始空格、分号、空元素和重复项。

registryType 保留原始注册表值类型，不隐式展开环境变量引用。

revision 标识对应目标的快照版本。

普通元素数组从 raw 派生，不作为另一份可独立修改的事实来源。

ElementRef

targetKey

snapshotId 或 sessionId

elementId

index

rawValue

元素 ID 的稳定范围限定为对应快照或编辑会话。

两个内容完全相同的重复元素仍拥有不同身份。

重新读取系统后的元素不自动继承旧快照 ID。

MatchResult

至少包含：

targetKey

matchedCount

totalCount

matched

missing

匹配沿用当前规则：

普通元素按分号拆分。

首尾空白仅用于比较，不修改原文。

大小写敏感。

空白比较结果为空的目标片段不计入比例。

重复目标逐项计数，但仅按存在性判定覆盖。

special 整体精确匹配，不拆分。

匹配信息不得被当成持久元素身份映射。

SelectionChange

只描述目标值编辑：

targetKey

beforeRaw

afterRaw

explicitElementEdits（可选）

普通文本输入只需要 beforeRaw/afterRaw。

存在明确编辑身份时，才记录元素级前后关系。

当用户切换来源、重新编辑整串或上下文失效时，不得继续使用过期的元素级说明。

ChangePlan

最小字段：

source：方案应用 / Windows 元素编辑。

targetKey

mode

special

baseRevision

before：包含 exists/raw/type。

desiredRaw

after：包含 exists/raw/type。

operations

explanations（可选，只读）

约束：

ChangePlan 是纯计算结果，不引用可变编辑会话。

operations 只包含确定的实际计划效果。

estimated 映射仅能放在 explanations，不能进入可执行 operations。

before/after 必须与 operations 一致。

无效或已过期计划不得执行。

不需要为每种 UI 标签增加独立布尔字段。

5. ChangePlan 生成规则
append / +append / -append

仅补充缺失的非空目标元素。

保留 Actual 原始文本。

保留已有空元素和重复项。

保留已有顺序。

不删除、不替换、不移动已有元素。

缺失判断为 trim 后大小写敏感的存在性比较。

相同 normalized 目标只补一次，保留首次出现的原始写法。

+append 前置缺失项。

-append 后置缺失项。

append 的自定义排序确认限制维持现状，不擅自实现新的排序策略。

当前值已经覆盖所有目标元素时，after 必须与 before 完全相同。

replace

以 Desired 原始字符串作为新的完整变量值。

不要求推导旧元素与新元素之间的一对一替换关系。

special

整个 raw 是一个不可拆分的值。

即使包含分号，也不能按普通列表处理。

Windows 元素编辑

由明确的编辑会话建立稳定元素身份关系。

允许记录新增、删除、替换、移动。

最终 after 以有效编辑行序列化结果为准，不以状态标签拼接结果。

底层写入语义

元素级 ADD/REMOVE/MOVE/REPLACE 是计划描述，不是 Windows 注册表的逐元素原子操作。

将来 Windows Adapter 负责对具体变量值进行完整写入、读取验证或删除变量值。

执行必须采用冻结计划的最终 after 值。

6. UI 数据契约（补齐精简版）

统一数据方向：

WindowsSnapshot + SelectedState → MatchResult + ChangePlan → ViewModel → UI

各页面职责如下：

页面	可展示数据	禁止事项
工作台	当前选定值、匹配、计划摘要、选定值编辑说明	自己推断 Windows 替换
Windows 环境页	当前快照、目标相关计划	根据字符串相似度猜替换
元素编辑器	编辑行、稳定身份变化、待追加候选、序列化结果	候选自动进入 live rows
预览	计划冻结的 before/after/operations	重新独立计算另一套结果
历史	实际演示应用的前后快照与确定操作	事后猜测元素身份

标签映射：

“匹配”：MatchResult。

“选定值已修改”：SelectionChange。

“待追加”：ChangePlan 中确定的 append ADD。

“待修改”：明确的实际元素修改操作。

“整体待替换”：明确的 replace 计划。

“移动”：稳定身份与顺序变化。

“重复”：独立提示，不代表执行操作。

颜色优先级继续由 UI 样式规则决定，不反向影响操作类型。

ViewModel 可以格式化文字、颜色和顺序，但不能创造新的业务操作。

7. 计划生命周期
浏览器演示

用户选择方案或编辑选定值。

应用服务取得当前演示 Snapshot 和 SelectedState。

纯函数计算 MatchResult、ChangePlan。

同一计划供工作台、对照和预览展示。

用户确认前，不改变 Windows 演示快照。

用户确认后，根据冻结计划更新演示数据。

记录不可变的实际 before/after。

更新匹配和计划展示。

取消、关闭、无变化不产生变化历史。

未来真实执行

生成计划与预览。

用户确认。

应用协调层重新读取相关目标。

验证相关目标的 exists/raw/type/revision。

如相关目标变化，则旧计划失效。

应用协调层重新生成计划，展示新的预览，等待再次确认。

执行器只执行已验证的冻结计划。

验证实际结果，记录执行事实。

无关目标发生变化，不应仅因全局快照版本改变就使所有计划失效。

如果计划依赖其他变量，则这些依赖也属于必须验证的读取范围。

执行器不得自行重新计算 Diff；重新生成计划属于应用协调层职责。

本轮不实现以上真实 Windows 执行过程。

8. V2 兼容与恢复保护

本轮仅处理 V3 浏览器演示。

不迁移 V2 核心代码。

不修改真实注册表。

不接入真实执行器。

不改变现有撤销与恢复规则。

不删除 V2 已有的回滚、历史或恢复保护。

旧 ExecutionProtocol 中“不强制自动回滚”不能解释为允许删除已有保护。

真实写入、失败恢复与部分成功处理，应在未来单独审查 V2 实际行为及其安全契约后确定。

9. 原方案 B 的保留与替代

原 B 方案中保留：

普通文本编辑不自动推断 Windows 元素替换。

明确 Windows 元素编辑使用稳定身份。

不凭文本相似度关联重复元素。

取消不写入快照。

被统一 ChangePlan 取代：

多个 UI 区域分别计算待追加或修改。

独立于操作计划的可执行 SelectionDiff。

依靠 UI 标记决定 append/replace 行为。

“选定值元素编辑入口”可以继续作为 UI 编辑方式，但它本身不赋予 Windows 替换权限，也不是本轮纵向案例的必要前置功能。

已经完成但尚未提交的 B 方案工作应逐项核对：

移除配置侧栏冗余变量组：可以独立保留。

纯 DemoPlan：若职责与统一 ChangePlan 一致，可作为其最小实现，不另建平行模型。

新选定值元素编辑入口：暂缓扩展，不与架构收敛一起强行提交。

10. 本轮唯一实施目标

先归档：

当前契约。

旧文档冲突清单。

适用规则的优先级说明。

然后只完成一条纵向演示：

Python Path 选定值变化 → 统一 MatchResult/ChangePlan → 工作台与对照 → 预览 → 演示应用 → 历史。

必须验证：

Scripts→Scripts1 的普通文本修改，选定值显示已编辑，append 只追加，不删除 Scripts。

编辑器明确修改 Windows 原元素后，实际结果为替换，历史按稳定身份记录。

空字符串与不存在不混淆。

空元素、重复、原文顺序不改变。

User/System 互不污染。

special 保持整体。

取消、无变化和旧计划失效不产生错误历史。

工作台、对照、预览使用同一有效计划，不能产生相互矛盾的操作描述。

本轮仍使用现有技术栈和浏览器演示数据。

不引入框架，不大规模重构，不接入真实 Windows，不合并 main，不发布 Release。

11. 文档优先级

发生冲突时：

负责人最新明确需求与确认。

本次最小执行契约。

已验证且未被本契约改变的 V2/V3 规则。

先前架构设计草案。

旧草案不得直接视为已经实现的项目事实。

不得将旧文档中的可选建议扩大成当前开发任务。

最终原则：先确定实际操作，再解释操作；不能先决定 UI 要显示什么，再反过来编造执行逻辑。
