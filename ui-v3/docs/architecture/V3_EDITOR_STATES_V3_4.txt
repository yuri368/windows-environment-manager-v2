【架构顾问 → Codex】

批准本轮最小修正方案。 我核对了 V3.3 的 windows-elements.js，问题确实来自 selectionPlan 的建议操作被投影到了本次编辑行和前后对照中。

最终裁定：采用一个紧凑的“方案建议”区域，加一行“本次编辑”状态摘要。 不建议做两个大型卡片。原有元素列表和前后对照本身已经能展示实际编辑变化，再增加一套完整变化面板只会制造重复信息。

还有一个容易漏掉的地方：除了 plannedRemoval()，现有 replacementExpected 也会让未编辑的行显示“将替换”。这次应一起消除同类语义混淆。

写作
V3.4 元素编辑器建议与实际编辑状态契约

状态：批准实施
适用范围：V3 元素编辑器
基线：V3.3，源码 36abaa1

一、核心原则

元素编辑器中必须区分两个来源：

方案建议（selectionPlan）

方案希望发生什么变化。

可以提供采纳建议的按钮。

不代表用户已经修改编辑列表。

不决定编辑器的应用结果。

本次编辑（session.plan）

用户当前实际修改了哪些元素。

包括手动修改及采纳建议产生的修改。

唯一决定编辑器前后对照、应用状态和历史结果。

由稳定元素 ID 的 audit 生成。

两者不得混用。

二、界面最小结构

保留现有布局，组织为：

元素编辑列表。

方案建议区。

可展开的元素变更对照。

底部本次编辑摘要与操作按钮。

不新增大型状态管理面板。

方案建议区

标题：

方案建议 · 尚未采纳

内容示例：

C　建议删除　[−]

E　建议追加　[＋]

按钮说明：

−：采纳建议，从本次编辑列表删除指定元素。

＋：采纳建议，将元素加入本次编辑列表。

区块说明：

“以下操作尚未纳入本次编辑，点击加减按钮仅修改编辑列表，不会立即写入 Windows。”

如果没有建议：

“没有尚待采纳的方案建议。”

底部本次编辑摘要

未修改时：

本次编辑：0 项变化 · 尚未采纳建议

发生变化时：

本次编辑：新增 1 · 删除 1 · 替换 0 · 移动 0

旁边保留原有“取消修改”和“应用（演示）”。

摘要来自 session.plan.operations，不读取 selectionPlan 的候选数量。

同一元素发生替换与移动时，可以分别计数，并沿用已有说明。

三、未采纳建议的显示位置
元素编辑列表

未采纳的删除建议不得让旧行显示：

待删除。

已删除。

将删除。

旧行仍按正常元素显示。

可以保留已有的匹配勾选、重复提示，但不得使用实际操作的删除颜色表示未采纳建议。

本轮不额外增加“建议删除”行内徽标，避免重复。建议只集中显示在方案建议区。

打开时的值

仅表示打开编辑器时的原始快照。

不叠加 selectionPlan 的建议标签。

编辑后的值

仅表示 session.plan 的实际编辑结果。

未采纳的新增建议不出现在这里。

未采纳的删除建议也不得使旧元素出现删除线。

实际删除后，才在对照里显示删除痕迹和 ghost。

整体替换建议

replacementExpected 不得在尚未实际编辑的行上生成“将替换”或其他确定性操作标签。

真正发生的整体替换或元素替换，仍由 session.plan.audit 展示。

四、采纳与手动编辑规则
采纳删除建议

点击 − 后：

找到方案建议对应的原始稳定元素 ID。

从 live rows 移除该元素。

重新生成 session.plan。

该删除建议从尚未采纳区域消失。

原始对照出现实际删除标记。

编辑后对照展示真实结果，并保留删除 ghost。

本次编辑摘要增加相应删除数量。

如果对应行已不存在或已被改写，不得继续操作旧建议。

采纳追加建议

点击 ＋ 后：

按对应模式插入 live rows。

赋予新的会话稳定元素 ID。

重新生成 session.plan。

已满足的追加建议消失。

编辑后对照出现实际新增元素。

摘要增加新增数量。

重复目标只产生必要的实际追加，不因重复 Selected 而额外添加。

手动编辑

用户直接修改旧元素，例如 C→E：

记录实际 REPLACE C→E。

原 C 的删除建议不再适用于该旧行。

如果 E 已满足方案的追加要求，E 的追加建议消失。

不把这次明确的编辑强行拆成 REMOVE+ADD。

用户直接删除旧行，或手动新增一个满足方案的元素时，对应建议也应即时消失。

建议变化由实时 live rows 重新计算，但不改变 selectionPlan 的原始事实。

五、还原、取消和应用
还原本次编辑

恢复打开弹窗时的原始 live rows。

session.plan 回到无变化。

曾采纳的方案建议重新出现。

删除 ghost 和实际编辑标签消失。

不改变演示 Windows 快照。

取消或关闭

丢弃整个编辑会话。

未采纳建议不执行。

已采纳但尚未应用的编辑也不执行。

不写入历史。

原演示快照保持不变。

再次打开时，根据当时有效的快照和方案重新展示建议。

应用（演示）

仅当 session.plan 存在有效实际操作时才能确认。

必须：

校验当前快照仍与编辑器打开时一致。

只应用 session.plan.after。

历史只记录 session.plan 的实际 before/after 和审计操作。

不把未采纳 selectionPlan.operations 合并进应用结果。

如果所有手动修改和采纳操作都已还原，应用按钮保持禁用。

六、过期与不确定建议
selectionPlan 已失效

方案建议区显示：

“方案建议已失效，需要重新检测。”

不展示可操作的确定性建议按钮。

不自动重建方案基线。

但这不意味着用户必须丢弃整个元素编辑会话：明确的手动编辑仍按其独立快照和操作校验处理，不新增额外限制。

Windows 快照发生变化

确认应用时按现有规则拒绝旧编辑，提示重新打开编辑器。

不执行过期 session.plan。

不生成成功历史。

重复 occurrence

不能确认具体删除对象时：

不生成可采纳的删除建议。

展示“存在重复，需明确选择元素”。

用户仍可以通过现有元素列表明确编辑具体稳定 ID。

共享元素

共享保护阻止自动删除时：

显示“共享保留”。

不提供确定性的建议删除按钮。

不暗示共享冲突已自动解决。

本轮不扩展已有显式编辑的共享保护规则。

七、实现边界

优先修改：

pendingMarkup 及候选文案。

plannedRemoval 的展示投影。

paintRow / token 中混入的方案建议标签。

candidatePlan 的建议展示。

元素编辑器底部摘要。

对应 DOM 和交互测试。

保留：

DemoPlan.buildElementEdit。

当前 stable ID audit。

原有 + / − 按钮。

当前 Undo/Restore、Cancel、Apply。

元素编辑器原有对照及联动能力。

V3.3 工作台三值对照。

不新增第二套编辑状态，不修改核心 ChangePlan 规则，不引入新框架，不访问真实注册表。

八、关键验收测试

必须覆盖：

打开编辑器，有建议删除 C，但 C 仍在 live rows，两个对照中均没有实际删除标记。

有建议追加 E，但 E 未加入 live rows，编辑后对照不得出现 E。

点击 − 后，实际删除 C，建议消失，原始/编辑后对照和摘要同步更新。

点击 ＋ 后，实际新增 E，建议消失，编辑后对照显示 E。

手动将 C 改为 E，实际操作为 REPLACE，原 C 删除建议和 E 追加建议均不再误导用户。

还原本次编辑，所有实际变化消失，未采纳建议恢复。

取消编辑，不修改 Windows 演示快照，不写历史。

只有建议、没有实际编辑时，Apply 禁用，摘要为 0 项。

重复 occurrence 和共享保护均不出现可执行的错误删除建议。

selectionPlan 失效后不能采纳旧建议，过期 session.plan 不能确认。

整体替换模式下，未执行编辑前不得出现“将替换”的确定操作标签。

点击 Apply 后，历史记录只包含本次真正采纳和手动编辑的操作。

九、最终裁定

方案建议只能引导编辑，不能伪装成编辑结果。

本次编辑才决定结果，而不是方案建议决定结果。

UI 只需要清楚地区分这两层，不需要为每一种建议状态再增加一套业务对象。

Codex，按此契约实施即可。这轮属于纯展示语义和交互反馈修正，不是新一轮架构重构。先保持现有紧凑布局，完成建议和实际编辑的区分，然后用打开、采纳、还原、取消、应用五种状态的截图验证即可。
