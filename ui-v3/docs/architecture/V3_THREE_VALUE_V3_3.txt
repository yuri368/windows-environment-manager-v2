一、三值对照界面

Windows 对照区调整为：

顶部：当前选定值

紧凑显示完整 Desired 原始字符串。

可以保留已有的匹配高亮。

选定值是目标，不代表已经应用。

恢复编辑、重新检测基线等控件仍可使用。

下方左侧：Windows 当前值

展示完整 Actual 原始元素列表。

保留所有未发生变化的元素。

确定的 REMOVE 在原位置显示“待删除”。

重复、空元素、空白以及原始顺序均保留。

需要确认的删除只能显示“删除需确认”，不能伪装成已确定操作。

下方右侧：应用后的值

完整展示冻结 ChangePlan.after。

保留未变化元素及其原始顺序。

已确定删除的元素不再出现。

已确定新增的元素在实际结果位置显示“待追加”。

不再额外堆叠旧删除候选或新增候选。

无变化时完整展示与 Actual 一致的结果。

宽屏左右并排，窄屏上下排列。

继续沿用已有元素编辑器的色块、字体和小标签，不重新创造一套视觉体系。

二、颜色和标签

匹配：沿用现有绿色提示。

待删除：沿用删除色系。

待追加：沿用新增色系。

重复、空元素：使用原有中性辅助样式。

删除需确认、共享保留：提示状态，不属于执行操作。

不得使用“待修改”描述普通文本输入。

“待删除”和“待追加”只能来源于确定的 ChangePlan.operations。

禁止根据字符串相似度生成展示关系。

三、元素关联

Actual 与 After 之间允许关联：

根据原始 beforeIndex 可以确定的保留元素。

根据确定性 ADD 操作及最终位置可以确定的新增元素。

保留元素即使出现重复字符串，也必须按原始 occurrence 身份关联，不能按文本查找第一个同名元素。

新增元素没有原始 Windows 身份，不能伪造它与某个已删除元素的对应关系。

悬停和键盘焦点联动只用于已确定的身份关系。

整个变量 replace 或 special=true 时，展示整体变化，不构造虚假的逐元素替换。

四、最后元素删除语义

最终结果区分三种状态：

情况 A：最后一个元素被删除

Before：

exists=true, raw="A"

用户从原选定值移除 A，且删除条件全部满足。

After：

exists=false, raw=null

含义：删除变量键。

情况 B：仍然保留原始空元素

Before：

exists=true, raw="A;"

实际元素为：

A

空元素

删除 A，保留原始空元素。

After：

exists=true, raw=""

含义：变量仍然存在，值为空字符串。

情况 C：用户明确创建空元素

用户在 Windows 元素编辑器中：

将已有元素明确编辑为空字符串，或

明确新增一个空元素并保留。

After：

exists=true, raw=""

含义：用户明确要求存在一个空值元素。

以上三种情况不得混淆。

如果编辑器删除全部 live rows，且没有保留空元素，结果应为变量不存在。

编辑器中“空列表应用后显示为空字符串”的旧提示也应同步修改，不能继续误导用户。

五、统一计划要求

最后元素删除语义适用于：

普通选定值编辑。

同目标批量计划。

显式 Windows 元素编辑。

三个入口必须获得一致的 exists/raw 结果。

ChangePlan.after 是唯一最终结果来源。

UI 不得通过单独拼接元素重新决定变量是否存在。

历史必须保存实际的 exists/raw 前后状态，不得仅用空字符串表示不存在。

六、同目标 Special 冲突

同一 scope + canonicalName 不允许同时使用：

special=true

special=false

即使 mode 均为 replace，且目标 raw 完全一致，也必须拒绝。

这个约束首先在本轮批量计划中实现并测试，不需要扩大为整个配置模块重构。

七、过期与无效计划

若 ChangePlan.valid=false：

Actual 仍显示当前已知快照。

当前选定值继续保留用户输入。

应用后的值不显示为确定结果。

显示“计划已失效，需要重新检测并预览”。

不展示确定性的待删除或待追加。

禁止确认应用。

重新建立基线仍需用户明确确认，不能后台自动处理。

八、编辑器与三值对照的边界

三值对照只负责展示。

原有元素编辑器继续负责：

新增。

删除。

替换。

移动。

待删除候选的减号操作。

待追加候选的加号操作。

点击加减候选只改变编辑器 live rows。

取消不改变 Actual。

不得因为对照区改版而再建立一个独立 Diff 计算器。

3. 应用后的值

这里你提的点很关键，我赞成：

应用后的值分成两层语义

A. 主展示层：结果对照视图

被删除元素以“幽灵 token”保留显示

B. 辅助文本层：最终写入字符串

小文本负责“精确表达最终结果”

这才严密。否则你把删除元素也放进“应用后的值”，视觉是爽了，语义却脏了，后面历史、预览、导出都会被你自己坑回去。

三、三栏联动高亮规则

这个我建议直接定死，不要再模糊。

规则 1：联动依据不是文本猜测，而是既有映射

联动必须基于已确定身份关系：

unchanged / retained 元素：按稳定 identity 联动

remove 元素：当前值 ↔ Windows 当前值 ↔ 应用后幽灵元素 联动

add 元素：当前选定值 ↔ 应用后的新增元素 联动

如果某栏不存在该元素，就只高亮存在的栏

规则 2：不做文本相似推断

不能因为两个 token 长得像就自动认为它们对应。

例如：

%PYTHON_HOME%\Scripts

%PYTHON_HOME%\Scripts1

这不是同一元素，只能由计划层明确告诉展示层：

这是 delete + add

还是 retain

还是 explicit replace

展示层自己不推理。

规则 3：hover / focus 一致

鼠标移入任一 token

或键盘 focus 到任一 token / 相关编辑行

其余两栏中有对应元素则同步高亮

高亮建议：

token 外框加深

背景提亮一点

标签不需要再变色，避免过吵

每个 token 的：
