## Astra 审查与修复

最终审查使用 `gpt-6-astra` / high，agent `01a15346-ac8d-7432-8817-269ad6acb6fe`，生产基线 `8e7f8d9`。检查计划审阅绑定、并发快照、持久执行/恢复与幂等、User/System 与 IPC、单实例/退出、升级保留，以及普通/幽灵拖动的数据身份。该轮未执行真实注册表或安装写入。

发现一项 P1：System helper 的写入被 CAS 拒绝后，若外部状态恰等于计划 after，旧补偿逻辑仍可能写回 before。Astra 使用生产 helper、Windows 适配器与内存 FakeWinreg 复现“外部写成相同 after”和“外部先删除”两种情况。原先自动化与原生验收未覆盖此分支；首个 3.0.0 构建 `163024-823` 因此被替代，不用于发布。

修复将自动补偿限定为本次适配器返回的完整写入快照及 revision，或本次已确认的类型转换中间快照。不能确认写入归属时，保留当前状态并进入 `recovery_required`。正常提交的 readback 同时核对适配器返回快照；进度、计划和 IPC 协议保持原格式。

新增两项使用生产 Windows 适配器和 FakeWinreg 的回归，断言 CAS 冲突后不存在 helper set/delete，外部状态保持原样。另明确“写后抛错且未返回确认快照”的恢复语义：先前已确认写入可补偿，当前不确定写入保留并待恢复。helper/IPC/System 服务定点回归执行 99 项：98 通过、1 项 opt-in 普通用户原生管道检查跳过。
